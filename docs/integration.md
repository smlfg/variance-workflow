# How variants coexist in the target repo

The workflow only works if five implementations of one feature can live in one tree without
merge conflicts and can be selected at runtime. That needs a **variant seam** in the target repo,
prepared by a human (or one model run) *before* the variant run.

## Rule that makes it conflict-free

Every variant owns a disjoint set of paths (`[feature].owned`, with `{id}`), and nothing else.
Shared files (registry, tests, CI, dependency files, README) are read-only for models. Then:

- variant branches never conflict with each other,
- `vw integrate` is just "check out each passing variant's owned paths onto one branch",
- out-of-scope edits are visible in the report but cannot leak into the integration branch.

## Integration modes

### 1. Plugin directory + registry (default, used by the demo)

```
src/textkit/slugify/__init__.py        # registry: discovers variants/v_*/; selects by arg or env
src/textkit/slugify/variants/v_ref/    # hand-written reference (optional)
src/textkit/slugify/variants/v_a/      # owned by variant a
src/textkit/slugify/variants/v_b/      # owned by variant b
```

Selection: `slugify(x, variant="b")` or `TEXTKIT_SLUGIFY=b`. Discovery means adding a variant
never edits a shared file. Works in any language with a module system or a `register()` call in
a file the variant owns (Go `init()`, TS barrel generated at build time, Rust feature-gated mod
generated by a build script).

### 2. Feature flag / config switch

Same layout, but the selected variant comes from a config file or a flag service
(`feature.slugify.variant = "c"`). Good for real A/B traffic splits: the comparison report tells
you *what* differs, the flag lets you measure *which users prefer what*.

### 3. Variant directories at the top level

`variants/a/`, `variants/b/`, ... each a complete mini-implementation (or app) with its own
entrypoint. Best when variants differ in architecture or UI rather than in one function.
Acceptance tests run per directory.

### 4. Branches only

Variants stay on `variant/<feature>/<id>-<model>` branches and are never combined; only the report
is merged. Cheapest, but you lose "selectable at runtime" and branches rot as `main` moves.

## Acceptance tests

- One shared suite; the variant under test comes from `VW_VARIANT` (`a` or `a,b,c`).
- The suite must fail if the requested variant does not exist (so "model wrote nothing" fails).
- Test the **contract** only. Everything the spec leaves open on purpose belongs in the probe
  set, not in the tests; otherwise the tests remove the variance you are paying for.
- A variant may add its own tests in a path it owns (e.g. `tests/variants/test_v_{id}.py`).

## Probes

`probe_cmd` gets the same inputs for every variant and prints `{input: output}` JSON. The report
lists every input where variants disagree. For non-function features, probes can be HTTP
responses, CLI outputs, rendered screenshots (as hashes or paths), timings, etc.
